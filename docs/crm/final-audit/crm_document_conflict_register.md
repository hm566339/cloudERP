## 1. Executive Summary

This register formally documents every technical contradiction, count discrepancy, architectural ambiguity, and service boundary overlap identified during the cross-document and cross-codebase audit of the Mark2 Cloud ERP CRM module.

Each conflict has been investigated against:
1. Actual source code implementations across backend microservices (`ERP_System`, `account-main`, `workflow-service`, `communication-service`, `gateway_service`).
2. Actual frontend React/Redux source code (`ERP/src/api/sales-crm/`, `ERP/src/features/sales/`).
3. Existing database schemas (`account-main/db/schema.dbml`, `workflow-service/workflow_schema.dbml`, `manufacturing/db/manufacturing.dbml`, `db/init.sql`).
4. System-wide API and subscription contracts ([`docs/API_CONTRACT.md`](file:///d:/final2/finalcode1/finalcode1/deploy-project/docs/API_CONTRACT.md), [`docs/SUBSCRIPTION_API_CONTRACT.md`](file:///d:/final2/finalcode1/finalcode1/deploy-project/docs/SUBSCRIPTION_API_CONTRACT.md)).

Every conflict has been assigned a definitive status: `RESOLVED` or `NEEDS DECISION`. **Zero resolutions are invented; every resolution is grounded in verified project evidence.**

## 3. Reconciliation Summary by Service

### 3.1 `workflow-service` Reconciliation
* **Finding:** All documents agree that `workflow-service` is the sole owner of approval state machines.
* **Resolution:** `crm-service` contains **0 approval tables**. It interfaces exclusively via `POST /api/v1/workflow/transactions` using document types `QUOTATION`, `DISCOUNT_APPROVAL`, `CUSTOMER_ONBOARDING`, and `LEAD_REASSIGNMENT`, with callbacks arriving at `/api/crm/workflows/callback`.

### 3.2 `account-main` Reconciliation
* **Finding:** Clear separation established between CRM sales negotiation documents and financial ledgers.
* **Resolution:** Pre-sales accounts (`crm_account`) link to `account-main.customer` via `account_main_customer_id`. Accepted CRM quotations (`crm_quotation`) convert to official ERP sales orders (`account-main.sales_order`) via event publishing to `crm_outbox`.

### 3.3 `inventory` Reconciliation
* **Finding:** Products and pricing belong strictly to `inventory`.
* **Resolution:** `crm_lead_product_interest`, `crm_opportunity_item`, and `crm_quotation_item` store `product_id` (UUID) as a logical foreign reference without physical cross-database constraints.

### 3.4 `communication-service` Reconciliation
* **Finding:** Communication infrastructure vs. conversational state.
* **Resolution:** `communication-service` handles delivery queues and template rendering; `crm-service` manages conversational threads (`crm_conversation`, `crm_message`, `crm_call_log`) and customer engagement history.

### 3.5 `ERP_System` (SSO & Subscription Billing) Reconciliation
* **Finding:** Tenant company context and module access.
* **Resolution:** Authenticated requests pass `X-Company-Id` header. `ERP_System` validates that the active subscription plan includes the `CRM` canonical module. `sso.user.id` is referenced across CRM entities without cross-DB constraints.
